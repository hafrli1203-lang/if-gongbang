# IF 공방

사용자(대표)의 판단을 작업 일지와 도면으로 쌓고, 그 기준과 울타리 안에서 AI 작업조가 프로젝트를 깎아
만들며, 시험대로 재어 조금씩 다듬어 가는 개발·운영 방식이다. Claude Code(또는 비슷한 에이전트
하네스)의 hook 기능 위에 얹어 쓴다.

자세한 개념은 `docs/concept.md`, 그림 안내서는 `docs/guide.html`을 본다.

**v3 — 전환 중(2026-11-01):** 입구 하나 → 작업 사본 → 플레이북 → 범위 검사 → 합치기·배포·자동
되돌림(지원 배포기 한정) → 보고. 카톡 접수·앱별 verify는 운영자 로컬 구현이며 이 저장소에는 아직
없다(`v3/` 추출 예정 — 현재 문서는 `docs/v3.md`, 추출 뒤 생성).

**v2 — 보관(2026-11-01):** 설계 `docs/v2.md`, 엔진 코드 `v2/`(사용법 `v2/README.md`). 절차가
코드가 되고 AI는 한 칸만 맡는 궤도(사실확정 → 실측 → 계획 → 시안 → 구현 → 검토 → 시험대 → 보고)를
실제로 돌렸던 설계다 — 운영 판단으로 더 쓰지 않게 됐다. 과제 5건에서 확인한 "범위 준수 5/5"(기록:
`v2/docs` STAGE3 관련 절)는 그 자체로 남겨 두되, v3의 scope-check는 **목적은 같지만 보장 범위가
다르다**(v2는 실행 관문·샌드박스로 변경 자체를 막는 실행 시점 검사, v3는 변경이 끝난 뒤 경로를 보는
사후 검사) — 같은 사례의 재시험 전에는 v3가 v2와 동등한 보호를 제공한다고 주장하지 않는다.

## 공방의 부품 10개

| 이름 | 하는 일 |
|---|---|
| **반장** | 일을 나누고 맡기고 확인하고 보고하는 메인 에이전트 |
| **작업조** | 깎는 손(구현)과 보는 눈(검수)을 따로 둔다 — 자기가 만든 것을 자기가 채점하지 않는다 |
| **울타리** | 사고를 지시문이 아니라 장치(hook)로 막는다 |
| **작업 일지** | 한 번 지적받은 것을 3문장으로 남긴다 — 아직 기준은 아니다 |
| **도면** | 반복 확인되고 승격된 작업 일지만 프로젝트의 정식 기준이 된다 |
| **곳간** | 참고 자료를 쌓고 근거로 꺼내 쓴다 |
| **시험대** | 좋아졌는지 나빠졌는지 숫자로 잰다 |
| **다듬질** | 한 바퀴씩 고치는 고리(아래) |
| **작업판** | 할 일을 한 곳에 모은다 |
| **사실 카드** | 프로젝트마다 "어느 설정이 운영인지·무엇을 건드리면 안 되는지"를 한 장으로 — 코드 안에
흩어진 하드코딩 대신 이 한 장만 보고 판단한다 |

## 일하는 순서

**완성하는 개발(모든 규칙보다 앞):** 검토·시험에서 떨어지면 다시 돌리지 않고 먼저 고친다. 같은
단계가 2번 떨어지면 자동 반복을 멈추고 메인 에이전트가 직접 구현해 통과시킨다. 멈춰서 묻는 승인은
두지 않는다(삭제·이동은 백업 뒤 진행·보고). 새 규칙·관문·검토 단계를 더하지 않고, 개발을 막는
규칙은 걷어낸다. 자동 파이프라인은 "끝까지 돌고, 걸리면 고친다"만 남긴다. 원문:
`docs/rules/MASTER.md` §0.

**다듬질 고리(모든 수정에):** 돌려 본다 → 원인을 가른다(자료·기준·지시문·도구) → 원인 자리 하나만
고친다 → 같은 평가로 전후를 숫자로 잰다 → 사람이 기준을 정한다.

**착수 전 보고(코드·설정을 고치기 전에):** 읽은 자료(파일:줄) / 예상 위험·병목 / 바꿀 파일 /
되돌리는 법, 네 가지를 먼저 쓴다.

**완료 보고:** 실행한 명령 · 출력의 핵심 숫자 · 미검증 항목. 출력 없이 "완료·통과·성공"이라 쓰지
않는다.

**마지막 교차 점검(권장):** 테스트와 1차 검수를 통과한 뒤, 같은 변경분을 다른 모델 계열에 읽기
전용으로 한 번 더 보인다. 인증·권한·결제·삭제·외부 연동·배포·설정 변경에는 꼭 넣는 것을 권장한다.

**검증 횟수(기본값 — 중복 검증을 줄이기 위한 것, 생략 허가가 아니다):**

| 바뀐 것 | 기본 검증 횟수 |
|---|---|
| 문서만 | 0회 |
| 일반 코드 | 시험 1회 |
| 인증·권한·결제·삭제·외부 연동·배포·설정 | 시험 1회 + 다른 모델 계열 교차 점검 1회 |

이 표는 **같은 검증을 몇 바퀴씩 반복하지 않는다**는 기본값이지, 필수 CI를 건너뛰거나 실패 후
재검증을 생략해도 된다는 뜻이 아니다 — **필수 CI·공개 저장소용 검사·고친 뒤 그 수정과 관련된
재검증은 이 횟수와 별개로 항상 수행한다.**

**토큰 아끼기:** 필요한 파일만 정확히 지정해서 읽는다. 작업을 전환할 때 컨텍스트를 정리한다. 가벼운
조회·구현·설계 판단에 각각 다른 크기의 모델을 맡기는 식으로 역할을 나눈다.

전체 규칙 틀: `docs/rules/WORKFLOW.md`, `docs/rules/MASTER.md`.

**속도 기본값(모든 일에):** 빠르게 끝내는 것도 품질의 일부로 본다. 반장의 작업 방식과 v2 엔진의 기본값이 같은 원칙을 따른다.
- 반장: 보고한 남은 일 목록을 위에서부터 끝내고, 목록에 없는 시험·확장·다른 프로젝트 작업은 사람에게 물은 뒤에만 한다. 겹치지 않는 일은 작업조를 동시에 돌리고(작업조마다 자기 git worktree), 고칠 것을 모아 고친 뒤 전체 시험은 끝에 한 번 돌린다.
- v2 엔진: 검수와 시험대를 동시에 돌리고, 시험대는 바뀐 파일과 관련된 시험과 음성 대조 시험부터 돌린다. 관련 시험이 없거나 삭제·이름 변경이 섞이면 전체 시험으로 돌아간다(`v2/ENGINE.md` 8절).
