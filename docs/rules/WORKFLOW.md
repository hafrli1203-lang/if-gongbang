# 작업 순서 — 다듬질 고리

프로젝트마다 CLAUDE.md/AGENTS.md 같은 파일에서 이 문서를 가져다 쓰도록 만들었다. 공통 규칙(사실
보고·정확히 파악·안전·업종 하드코딩 금지)은 `MASTER.md`에 있다.

## 1. 다듬질(고리 한 바퀴) — 모든 수정에

돌려 본다 → 원인을 가른다(자료·기준·지시문·도구) → 원인 자리 하나만 고친다 → 같은 평가로 전후를
숫자로 잰다 → 대표가 기준을 정한다.

## 2. 착수 전 보고 — 코드·설정을 고치기 전에 반드시

1. 읽은 자료: 파일:줄 목록 (그 프로젝트의 결정 문서 해당 절, 세션 시작 때 보인 작업 일지 중 이번
   일에 걸리는 번호 포함)
2. 예상 위험·병목: 무엇이 깨질 수 있고, 무엇이 오래 걸리거나 막힐 수 있는가
3. 바꿀 파일
4. 되돌리는 법

네 가지를 쓰기 전에는 수정하지 않는다. 작은 문서 수정은 한 줄로 줄여도 된다.

## 3. 완료 보고

실행한 명령 · 출력의 핵심 숫자 · 미검증 항목. 출력 없이 "완료·통과·성공"이라 쓰지 않는다. 이번
일에서 나온 지적은 작업 일지에 남기고 번호를 적는다.

## 3-1. 마지막 교차 점검 (권장)

코드 변경은 테스트·1차 검수를 통과한 뒤 **같은 diff를 다른 모델 계열에 읽기 전용으로** 넘긴다. P0·P1은
반영 후 다시 점검(최대 2번), P2는 판단, P3는 기록. 필수로 두는 것을 권장하는 영역: 인증·권한·결제·
삭제·외부 연동·배포·설정 변경. 생략해도 되는 영역: 문서·문구.

## 3-2. 속도 기본값 — 모든 일에
빠르게 개발하는 것도 개발의 목적이다.
- 보고한 남은 일 목록을 위에서부터 끝낸다. 목록에 없는 시험·확장·다른 프로젝트 작업은 끼우지 않는다(사람에게 물어서만).
- 겹치지 않는 일은 작업조를 동시에 돌린다(작업조마다 자기 git worktree).
- 고칠 것은 한 번에 모아 고치고, 전체 시험·실제 실행은 끝에 한 번. 실제 실행으로 결함을 하나씩 찾는 고리를 반복하지 않는다.
- 오래 걸리는 시험은 전경에서 돌린다. 사람이 "대답만"을 요청하면 도구를 쓰지 않고 답만 한다.

## 4. 자료를 찾을 때

참고 자료가 있는 프로젝트는 "앱 폴더를 뒤지기 전에 자료 검색 도구를 먼저 쓴다"는 규칙을 둔다. 검색
없이 기억으로 답하지 않는다.

## 5. 큰 일의 흐름 (3개 파일 이상 또는 되돌리기 어려운 일)

구상(무엇·왜) → 세부 계획 → 대표 승인 → 구현(한 단계씩, 고리대로) → 막히면 질문 → 인계. 검증
실패·회귀·반복 지적이 생기면 더 엄격한 방식(검수 담당을 별도 에이전트로)으로 바꾼다.

## 6. 할 일의 원천

워크스페이스 전체 할 일은 한 작업판 파일 하나(`work_queue_path`)에 둔다. 프로젝트의 결정은 그
프로젝트의 결정 문서 하나에 둔다.
