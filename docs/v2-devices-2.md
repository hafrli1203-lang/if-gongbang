## 울타리 — 막는 훅

| 훅 | 언제 | 무엇을 막나 |
|---|---|---|
| 일 시작·닫기 | `/일 <이름>` · `일 닫기 <이름> <사유>` | 이미 열린 일이 있으면 두 번째 일 폴더 생성 차단. 열린 동안 들어온 대표 지적(`지적 ` 머리말)은 훅이 원문 그대로 작업 일지에 「대기」로 적고, 대표가 `일 닫기`를 치는 순간 훅이 대기열 맨 앞 지적으로 ⓪ 일을 연다. 비정상 종료로 열린 채 남은 일은 **대표만** 사유를 적어 닫는다 |
| 편집 | 편집·쓰기 | 소스 폴더는 ⑤ 칸에서 소유표 안만. `scripts/probe/`는 ② 칸의 실측자만. `tests/bench/`는 둘로 나뉜다 — 케이스 본체는 **시험자 ∧ ⓪ 칸 ∧ 새 파일**일 때만(번호는 실행기가 자동 부여), `tests/bench/scenes/`(통과 장면 스크립트)는 **시험자 ∧ (③ 칸 또는 「명령 오류」 되돌림 중)**일 때만, **다음 번호 이름으로만** 쓰기 허용. 고친 이력은 AI가 적은 글이 아니라 **훅의 편집 기록**과 ⑥에서 대조. 보호 파일은 누구도 못 씀 |
| 커밋 | 커밋(글자가 아니라 git 자체의 **pre-commit 훅**에도 같은 검사; 터미널 허용 목록은 `--no-verify`와 `git -c`를 통과시키지 않는다) | review.md 통과 + bench.json pass **+ 두 파일에 적힌 코드 지문(트리 해시)이 지금 올라갈 코드의 지문과 같을 것**. 다르거나 지문이 없으면 ⑥으로(시험만 다시 돌려도 검토는 다시 되지 않는다). bench.json과 지문은 보호 파일이라 믿는다. 커밋은 **궤도 스크립트**가 친다 — 직원은 못 치고, 대표는 배포 승인만 한다 |
| 배포 | 배포 스크립트, 그리고 main push로 배포가 자동 실행되는 프로젝트는 PC 쪽 push 훅이 아니라 **서버 쪽 자동 검사**(CI/서버 훅 — 그 설정 파일도 보호 목록)에 | ⑥⑦ 산출물 + 코드 지문 일치 + 교차 점검 결과 도착 전엔 차단 |
| 작업조 | 작업조 생성 | ⑤⑥ 칸에서 역할 직원이 아닌 범용 작업조 차단 |
| 상태 줄 | 답이 끝날 때 | 금지어 검사는 쓰지 않는다("끝났습니다"로 피해 간다). 일이 열려 있으면 훅이 답 끝에 **"현재 칸 ④ · 미검증"** 같은 상태 줄을 자동으로 붙인다 — 어떤 표현을 쓰든 실제 상태가 같이 보인다 |
| 반장 터미널 | 일이 열린 동안 | 반장의 터미널 명령 전부 차단, 호출 수 초과 시 차단("새 창" 안내) |
| 터미널 | 직원의 터미널 명령 | 금지 목록이 아니라 **허용 목록**(화이트리스트)에 있는 명령만 통과(`python -c`·`node -e`·`perl -i`·`git checkout <파일>`·`git apply`·`curl -o` 같은 우회는 목록에 없으므로 막힘). 명령이 끝나면 `git status`로 허용 경로 밖 변경을 보고, 있으면 되돌린 뒤 막는다. 벽은 샌드박스 |
| 공개 저장소 push | `git push` | 금지 목록(빌려온 이름·사람 이름·내부 주소·경로·메일·계정명·날짜·일지 번호·승인 예시)에 걸리면 차단 |
| 시험대 보호 | 편집·쓰기 | 구현 칸에서 `tests/bench/` 편집 차단, `bench.json` 직접 쓰기 차단(시험 실행기만 씀 — 시험자가 고치는 것은 케이스·장면 스크립트이지 실행기가 아니다) |
| 승인 범위 | `승인 <이름>` | 이름이 열린 일·프로젝트와 맞지 않으면 거절하고 다시 입력받음. 배포·삭제는 짧은 창을 따로 둠(설정값) |
| v1 유지 | — | 승인 관문(`승인 <이름>`), 위험 명령, 비밀 파일, 훅 자체 보호 |

- 임계값과 민감 영역 패턴은 훅이 읽는 **설정 파일**에 둔다. 고치는 것은 승인 관문이다(아래 「보호 파일 목록」).
- v2를 적용할 **프로젝트 목록**이 보호된 설정에 있다. 목록에 있는 프로젝트는 상태 파일이 **늘 있어야** 하고, 그 값이 「닫힘」일
  때만 v2 훅이 쉬며, **파일이 없거나 못 읽으면 막는다**("열린 일 없음"으로 읽지 않는다). 목록에 없는 프로젝트에서는 v2가 꺼져 있다.
  목록에서 빼는 것도 승인 관문으로만 한다. 되돌리기는 설정에서 훅 몇 줄을 빼는 것이다.

## 시험 케이스는 쌓기만 하지 않는다

- 케이스마다 **어느 지적에서 나왔는지**(작업 일지 번호)와 **어느 기준(도면)에 묶이는지**를 적는다.
- 도면이 바뀌어 더는 맞지 않는 케이스를 정리하는 것도 **대표 승인**이다. 도면 변경과 케이스 정리를 한 묶음으로 올려 승인받고, 기준 변경 보고에 "정리한 케이스" 칸을 둔다(도면 자체도 보호 파일이라 AI가 고쳐서 케이스를 걷어낼 수 없다).
- 결과가 들쭉날쭉한 케이스는 「불안정」으로 표시한다: **통과 수에서는 빼되 ⑦은 막는다.** 따로 고친다. **불안정 판정은 사람도 AI도 하지 않는다** —
  시험 실행기가 같은 코드로 여러 번(설정값, 처음 값 5회) 다시 돌려 결과가 갈릴 때만 붙이고, 불안정으로 넘어간 케이스 수는 보고에
  반드시 찍힌다. **불안정은 통과가 아니다** — 불안정 케이스가 하나라도 있으면 ⑦은 열리지 않고, 고쳐서 안정이 되거나
  대표가 그 케이스를 따로 판단해야 한다(면제는 원문 기록의 승인 메시지 번호와 맞을 때만 인정하고, 날짜와 유효 기한을 적는다 — 예: 다음 일까지. 영구 면제는 없다). 구현자는 `tests/bench/`를 못 고치므로 **불안정 판정이 나면 시험자에게 넘어간다** —
  원인이 케이스·장면 스크립트 쪽이면 시험자가 고치고, 코드 쪽이면 시험자가 재현 조건을 케이스에 적어 구현 칸으로 보낸다. 가끔만 터지는 진짜 버그가 불안정 뒤에 숨는 것을 막는다.
- **케이스 수가 줄면 실패다.** 시험대는 이전 실행의 케이스 수를 기억하고, 수가 줄었으면 pass를 내지 않는다
  (정리한 케이스는 예외이되, 그 보고가 아니라 **원문 기록의 승인 메시지 번호**와 맞을 때만 — AI가 쓴 보고는 예외 근거가 아니다).
- **지적 → 케이스는 시험자가 ⓪ 시험 등록 칸에서 쓴다.** 대표 지적이 들어오면 반장이 작업 일지에 남기고 **그 지적으로 새 일을 연다.**
  그 일의 첫 칸이 ⓪ 시험 등록이다: 시험자가 케이스를 쓰고 **현재 코드에서 실패하는 실행 기록**을 남긴다. 그다음 ①~⑥을 지나
  ⑦에서 통과 기록이 남아야 케이스가 등록된다. 순서는 코드에 고정되어 "두 번째 일 차단"과 꼬이지 않는다(지적 일 하나 = 일 하나).
- **⓪에서는 새 파일만 더할 수 있다.** 기존 케이스를 고치거나 지우는 것은 재발 0이 무너지는 자리라 대표 승인으로만 열린다.
  케이스 번호는 훅이 **다음 번호만** 허용해 겹침이 처음부터 생기지 않고, 그래도 겹치면 실패로 처리한다. 이전 케이스 수를 기억하는 파일은 보호 파일이며, **수동 케이스 수가 줄어도** 실패다.
- **자동 시험으로 실패를 재현할 수 없는 지적**(디자인 취향, 문구 느낌)은 ⓪을 영원히 못 빠져나가므로 출구를 둔다: 대표가
  "자동 시험 불가"를 고르면 「수동 케이스」로 등록되고 ⓪은 닫힌다. 수동 케이스는 검토자의 화면 품질 판정표에 줄 하나로
  들어가며, "고치기 전 실패·고친 뒤 통과" 대신 **고치기 전 캡처·고친 뒤 캡처·검토자 판정 줄**을 요구한다. 자동 케이스와
  섞지 않고 수를 따로 센다.
- **케이스는 "고치기 전 실패 · 고친 뒤 통과" 둘 다 확인돼야 등록된다.** 새 케이스를 고치기 전 코드에서 돌려 실제로
  실패하는 것을 실행 기록으로 남기고, 고친 뒤 통과하는 것도 기록으로 남긴다. 둘 중 하나라도 없으면 시험대에 들어가지
  않는다 — 아무것도 못 잡는 케이스가 쌓이는 것을 막는다. 이것이 "재발 0"이 말이 아니라 장치가 되는 지점이다.

## 상한값과 설치는 기록으로 관리한다

- 호출 상한·바퀴 상한·시간 상한·소형 궤도 파일 수는 처음 값이 정답이 아니다(터미널 비율은 상한이 아니라 계기판 지표다). 설정 파일에 **바꾼 날과 이유**를 함께 적고,
  계기판 숫자(막힘이 너무 잦은가, 너무 느슨한가)로 조정한다.
- 설치 뒤에는 읽기 전용 점검 스크립트로 훅이 실제로 등록됐는지 확인한다. 저장소에는 push마다 테스트가 자동으로
  돌게 하여(CI) 울타리 코드 자체가 망가지는 것을 막는다.


**역할을 무엇으로 구분하나.** 반장 터미널·작업조·터미널 훅은 "누가 명령했는지"를 알아야 작동한다. 훅 입력에 직원 식별이
들어오는지 첫 시험에서 확인하고, 들어오지 않으면 **직원마다 별도 작업 사본(폴더)**을 주어 경로로 역할을 구분한다(경로 = 역할).
확인되기 전까지 역할별 훅 세 개는 "추정"으로 표시한다.

## 보호 파일 목록 — AI가 쓸 수 없고 훅·궤도 스크립트만 쓴다

쓰기·편집 도구와 샌드박스 양쪽에 같은 거부 규칙이 걸린다. 고치는 길은 **대표 승인 관문 하나**뿐이고, 바꾼 날과 이유가 기록된다.

| 파일 | 왜 보호하나 |
|---|---|
| 일 상태 파일(열린 일, 현재 칸, 건너뜀 기록) | 칸 숫자를 바꾸거나 표시를 지우면 울타리 전체가 꺼진다. **칸 이동과 일 닫기는 궤도 스크립트만** 하고, 앞 칸 산출물을 확인한 뒤에만 넘어간다 |
| 설정 파일(임계값·민감 영역 패턴·경고/차단 모드) | 느슨하게 고치면 모든 관문이 느슨해진다 |
| 훅 스크립트 폴더, 훅을 등록하는 **전역 설정 파일**, **하네스 설치 폴더**, **각 프로젝트의 `.claude/` 설정** | 훅 하나를 고치거나 프로젝트 설정으로 훅을 끄면 장치가 한꺼번에 꺼진다 |
| **`.git/` 전체 읽기 전용**(직원은 커밋을 하지 않으므로 쓸 일이 없다; hooks·config·info만 막으면 refs·HEAD·packed-refs로 가지가 가리키는 커밋을 옮길 수 있다), 서버 쪽 자동 검사 설정 | pre-commit 훅·push 검사·가지 위치를 바꾸는 자리. 읽기 전용에서 깨지는 명령이 있으면 그 명령 하나만 따로 확인 |
| 실행 기록, 원문 기록, 열람 기록 | 검사의 근거 — 고치면 자기신고가 된다 |
| `bench.json`, 이전 케이스 수 파일 | 시험 결과와 "케이스 수가 줄었는지"의 기준 |
| 코드 지문(검토·시험을 마친 시점의 트리 해시) | 커밋 관문이 "지금 코드"에 대한 통과인지 확인하는 기준 |

**설치본은 저장소와 직접 연결하지 않는다.** 장치의 원본은 이 저장소의 `harness/`지만, 설치본은 **버전을 고정한 복사본**이다(저장소를 가리키는 심볼릭 링크 금지 — 링크면 저장소 쪽 파일을 고치는 길이 남는다).
이 저장소를 `/일`로 고치는 날 구현자가 손대는 파일이 바로 자기를 막고 있는 훅이기 때문이다. 보호 폴더에 복사하는 설치 절차는 **AI가 아니라 대표가 본인 터미널에서** 돌린다(AI 쪽은 그 폴더에 쓸 수 없다). 새 버전 설치는
승인 관문을 거친 뒤 점검 스크립트가 등록 상태를 확인할 때만 한다.

## 시험은 샌드박스 밖에서 돈다 — 시험받는 코드가 결과를 못 고치게

bench.json·실행 기록·코드 지문·이전 케이스 수는 보호 파일이라 직원도, 직원이 터미널에서 띄운 시험 스크립트도 쓸 수 없다.
그래서 시험은 직원이 돌리지 않는다. **직원은 실행을 요청만** 하고, 궤도 스크립트(훅)가 **샌드박스 밖에서** 시험을 띄운다.
시험받는 코드(구현자가 쓴 것)는 다시 **샌드박스 안**에서 돌고, 결과 파일은 그 코드가 끝난 뒤 **별도 단계**가 샌드박스 밖에서
쓴다. 시험받는 코드가 돌면서 bench.json이나 케이스 수 파일을 고치는 길이 없다. 실행 기록과 코드 지문도 같은 방식이다.
훅이 실제로 샌드박스 밖에서 도는지는 「첫 시험에서 확인할 항목」에 있다.

## 시험대·케이스·일지·도면 보호

- **새 파일 이름은 번호 형식만**: ⓪의 케이스도, ③의 `tests/bench/scenes/` 장면 스크립트도 **다음 번호 이름으로만 쓰기를 훅이 허용**한다(이름은 쓰는 순간 정해진다). 실행기는 형식에 맞는 파일만 모은다. 시험 도구가 자동으로 읽는 이름(예: pytest의
  `conftest.py`)을 새 파일로 넣으면 기존 케이스 전부의 동작을 바꿔 통과시킬 수 있고 케이스 수 감소 검사에도 안 걸리기 때문이다.
- 구현 칸에서 고칠 수 있는 **프로젝트 시험 설정**(`package.json`의 test 줄, jest·pytest 설정)도 같은 길이다. 실행기는 프로젝트
  설정 대신 **하네스 쪽 고정 설정**으로 돌고, 프로젝트 안의 시험 설정 파일은 시험대 보호에 넣는다. 시험 실행기 파일 자체는
  **전역(하네스 설치 폴더)**에 있고 보호 파일이다.
- **도면**(결정 문서)은 보호 파일이다. 도면을 바꾸는 것은 케이스 정리와 한 묶음으로 대표 승인이다.
- **작업 일지는 덧붙이기만** 된다. 두 갈래로 막는다: 편집 도구는 기존 내용이 앞부분에 그대로 남는지 훅이 검사하고, 터미널의
  `>` 덮어쓰기는 일지를 보호 경로에 두어 막는다 — 덧붙이기는 궤도 스크립트에 **요청**하는 방식이다. 케이스가 근거로 가리키는 곳이기 때문이다.
- `scripts/probe/`의 실측 로그는 **훅이 실제 실행에서 남긴 것만** 인정한다. 직원이 손으로 쓴 로그는 "실측"이 아니다.
- **수동 케이스는 다시 올라온다**: ⓪에서 수동 케이스마다 **묶인 파일 경로 패턴**을 같이 적고, 어느 일에서든 바뀐 파일 목록이 그
  패턴과 겹치면 검토자 판정표에 그 줄이 자동으로 다시 올라온다("관련 있는지"를 AI가 판단하지 않는다). 패턴이 비어 있는 케이스는
  매번 올라온다.

## 터미널 명령 판정 — 첫 단어가 아니라 명령 전체

허용 목록은 첫 단어로 판정하지 않는다. 명령을 `&&`, `||`, `&`, `;`, `|`, `$( )`, 백틱, 줄바꿈, `<( )`, here-doc 단위로 **쪼개
하나씩** 판정하고, 쪼갤 수 없는 명령은 거부한다. **앞에 붙은 환경 변수는 떼고 보지 않는다 — 접두가 붙으면 거부**하고 꼭 필요한
변수만 허용 목록에 둔다. **거부 예시**(허용이 아니다): `GIT_CONFIG_COUNT`·`GIT_CONFIG_KEY_0=core.hooksPath`처럼 설정을 환경 변수로
넣는 것, `GIT_DIR`, `NODE_OPTIONS`, `PYTHONPATH`, `LD_PRELOAD`. `git`은 하위 명령뿐 아니라 인자까지 본다 — `--no-verify`는 통과하지 않고, **`git` 바로 뒤에 오는 옵션은 전부 불허**한다
(`-c`, `-C`, `--git-dir`, `--work-tree`, `--namespace`, `--exec-path`, `--config-env` … 이름을 세지 않는다). 쪼개는 기준의 `$( )`와
백틱은 같은 줄에 있다. `claude`(새 세션을 열면 v2 훅이 전부 쉰다), `bash -c`, `sh -c`, `xargs`,
`find -exec`, `env`, `eval`, `exec`는 허용 목록에 없다. 허용 목록 안의 `npm run`·`pytest`·`node <파일>`은 프로젝트 코드를 그대로
돌리므로 그 자체로는 아무것도 막지 못한다 — 벽은 샌드박스다.

명령 뒤의 `git status` 점검에는 보지 못하는 곳이 있다: `.git` 안의 변경, `.gitignore`에 걸린 파일, 저장소 밖 파일. 보호
목록의 `.git/hooks`와 전역 설정이 바로 이 사각지대에 있으므로, **그 자리는 샌드박스 거부 규칙만이 막는다.** 네트워크 전송·
배포처럼 되돌릴 수 없는 일은 사후 점검으로 막지 못하므로 **샌드박스의 네트워크 허용 주소**로 막는다. 되돌리기는 HEAD 기준이 아니다(직원은 커밋을 못 하므로 앞 칸의 변경이 전부 커밋 전 상태라, HEAD로 되돌리면 앞 칸 작업까지
사라진다). 칸이 시작할 때 해시만이 아니라 **내용 사본**을 떠 두고 거기서 복원한다. **칸이 시작할 때 목록에 없던 파일만** 지우는
단계까지 넣고, 명령 뒤 점검은 `git status --ignored`로 무시 목록 파일까지 본다(지문·사본 비교와 같은 범위)(`git clean`처럼 무시 목록 파일까지 지우면 `.env`나
의존성 폴더가 날아간다), 범위는 그 직원의 작업 사본 안 허용 경로 밖 변경으로 한정한다(직원은
원본이 아니라 자기 사본에서 일하므로 대표가 같은 시간에 고친 원본 파일은 건드리지 않는다).

## 꺼지는 대신 막히게 — 상태 파일과 /일

- "일 폴더가 열려 있지 않으면 아무것도 하지 않는다"는 규칙은 상태 파일이 **깨지거나 읽히지 않을 때도** 꺼진 것으로 읽는다.
  상태 파일을 못 읽으면 **막는 쪽**(fail-closed)으로 처리한다. 일 중단·포기도 궤도 스크립트를 통하며 대표 승인을 거친다.
- `/일`·`일 닫기`·`승인`·중단·포기·`지적 ` 머리말은 대표만 부른다. 명령 파일 머리에 **모델 호출 금지 설정**(`disable-model-invocation`)을
  넣고, 훅이 그 입력이 **대표에게서 왔는지** 확인한다 — 여섯 모두에. 이 설정이 설치한 버전에서 실제로 작동하는지는 첫 시험에서 확인한다.
- 커밋은 직원이 직접 치지 않는다. 구현자는 커밋을 **요청**하고, 커밋 관문 훅(궤도 스크립트)이 소유표 안 파일만 골라 커밋한다.

## 작업 사본 합치기

직원마다 작업 사본을 쓰면 **합치는 순간**이 새 통로다. 합치기는 검토자 통과 뒤 ⑥ 칸 끝에서 **궤도 스크립트만** 하고, 합친
결과의 코드 지문이 검토·시험을 마친 지문과 같은지 대조한다. 다르면 **자동으로 ⑥**으로 되돌리고, 합치다 충돌이 나면 궤도
스크립트가 직접 풀지 않고 **멈춘다**.

## 열린 일 중에 대표 지적이 오면

둘 중 하나로 정한다 — **대기열**이다. 대표가 `지적 <내용>` 머리말로 보내면 훅이 **원문 기록에서 그대로** 작업 일지에 「대기」로
덧붙인다(AI가 요약해 적지 않는다). 지금 일은 계속한다. **대기열의 일을 여는 주체는 반장이 아니다** — 대표가 `일 닫기`를 치는
순간 훅이 대기열 맨 앞 지적으로 ⓪ 일을 연다. 여는 주체가 대표 입력에 묶여 있어 모델이 일을 여는 길이 없다. 훅은 대기열을 **일지가 아니라 원문 기록의 메시지 번호로만**
읽는다 — 일지의 「대기」 줄은 보는 용도일 뿐이고, 편집 도구로 「대기」 모양의 줄을 쓰는 것은 막는다(AI가 「대기」 줄을 덧붙여 다음
일을 여는 길을 없앤다). 지금 일을 멈추고 지적부터 하려면 대표가 `일 닫기 <이름> <사유>`로 닫는다(승인).
지적이 사라지는 길은 없다: 「대기」 줄은 덧붙이기만 되는 일지에 있다.

## 첫 시험에서 확인할 항목 (확인되기 전까지 "추정")

1. 훅 입력에 직원 식별이 들어오는가(없으면 직원마다 작업 사본 = 경로로 구분).
2. 훅과 시험 스크립트가 실제로 **샌드박스 밖**에서 도는가.
3. `/일`의 모델 호출 금지 설정이 설치한 버전에서 작동하는가.
4. 세션 시작 점검이 샌드박스 켜짐·보호 경로 쓰기 거부를 실제로 확인하는가.
5. 프로젝트 안의 시험 설정을 실행기가 정말 읽지 않는가: 케이스 하나를 빼는 설정(그리고 `conftest.py` 같은 자동 실행 파일)을
   프로젝트에 넣고도 그 케이스가 도는지 본다 — 많은 테스트 도구가 프로젝트 설정을 자동으로 찾아 읽으므로 문장만으로는 보장되지 않는다.
6. 뚫리는 장면 재현: 상태 파일 손상 → 막히는가 / 예전 bench.json으로 커밋 → 막히는가 / `conftest.py` 새 파일 → 막히는가 /
   `git -c core.hooksPath=` → 막히는가 / `claude` 재호출 → 막히는가.
