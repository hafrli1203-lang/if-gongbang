# 검토용 3/5 — 검사·훅·케이스·설치 (12차 반영판)

- **지적 → 케이스는 시험자가 ⓪ 시험 등록 칸에서 쓴다.** 대표 지적이 들어오면 반장이 작업 일지에 남기고 **그 지적으로 새 일을 연다.**
  그 일의 첫 칸이 ⓪ 시험 등록이다: 시험자가 케이스를 쓰고 **현재 코드에서 실패하는 실행 기록**을 남긴다. 그다음 ①~⑥을 지나
  ⑦에서 통과 기록이 남아야 케이스가 등록된다. 순서는 코드에 고정되어 "두 번째 일 차단"과 꼬이지 않는다(지적 일 하나 = 일 하나).
- **⓪에서는 새 파일만 더할 수 있다.** 기존 케이스를 고치거나 지우는 것은 재발 0이 무너지는 자리라 대표 승인으로만 열린다.
  케이스 번호는 **실행기가 자동으로 매겨** 겹침이 처음부터 생기지 않고, 그래도 겹치면 실패로 처리한다. 이전 케이스 수를 기억하는 파일은 보호 파일이며, **수동 케이스 수가 줄어도** 실패다.
- **자동 시험으로 실패를 재현할 수 없는 지적**(디자인 취향, 문구 느낌)은 ⓪을 영원히 못 빠져나가므로 출구를 둔다: 대표가
  "자동 시험 불가"를 고르면 「수동 케이스」로 등록되고 ⓪은 닫힌다. 수동 케이스는 검토자의 화면 품질 판정표에 줄 하나로
  들어가며, "고치기 전 실패·고친 뒤 통과" 대신 **고치기 전 캡처·고친 뒤 캡처·검토자 판정 줄**을 요구한다. 자동 케이스와
  섞지 않고 수를 따로 센다.
- **케이스는 "고치기 전 실패 · 고친 뒤 통과" 둘 다 확인돼야 등록된다.** 새 케이스를 고치기 전 코드에서 돌려 실제로
  실패하는 것을 실행 기록으로 남기고, 고친 뒤 통과하는 것도 기록으로 남긴다. 둘 중 하나라도 없으면 시험대에 들어가지
  않는다 — 아무것도 못 잡는 케이스가 쌓이는 것을 막는다. 이것이 "재발 0"이 말이 아니라 장치가 되는 지점이다.

## 상한값과 설치는 기록으로 관리한다

- 호출 상한·바퀴 상한·시간 상한·소형 궤도 파일 수는 처음 값이 정답이 아니다(터미널 비율은 상한이 아니라 계기판 지표다). 설정 파일에 **바꾼 날과 이유**를 함께 적고,
  계기판 숫자(막힘이 너무 잦은가, 너무 느슨한가)로 조정한다.
- 설치 뒤에는 읽기 전용 점검 스크립트로 훅이 실제로 등록됐는지 확인한다. 저장소에는 push마다 테스트가 자동으로
  돌게 하여(CI) 울타리 코드 자체가 망가지는 것을 막는다.


**역할을 무엇으로 구분하나.** 반장 터미널·작업조·터미널 훅은 "누가 명령했는지"를 알아야 작동한다. 훅 입력에 직원 식별이
들어오는지 첫 시험에서 확인하고, 들어오지 않으면 **직원마다 별도 작업 사본(폴더)**을 주어 경로로 역할을 구분한다(경로 = 역할).
확인되기 전까지 역할별 훅 세 개는 "추정"으로 표시한다.

## 보호 파일 목록 — AI가 쓸 수 없고 훅·궤도 스크립트만 쓴다

쓰기·편집 도구와 샌드박스 양쪽에 같은 거부 규칙이 걸린다. 고치는 길은 **대표 승인 관문 하나**뿐이고, 바꾼 날과 이유가 기록된다.

| 파일 | 왜 보호하나 |
|---|---|
| 일 상태 파일(열린 일, 현재 칸, 건너뜀 기록) | 칸 숫자를 바꾸거나 표시를 지우면 울타리 전체가 꺼진다. **칸 이동과 일 닫기는 궤도 스크립트만** 하고, 앞 칸 산출물을 확인한 뒤에만 넘어간다 |
| 설정 파일(임계값·민감 영역 패턴·경고/차단 모드) | 느슨하게 고치면 모든 관문이 느슨해진다 |
| 훅 스크립트 폴더, 훅을 등록하는 **전역 설정 파일**, **하네스 설치 폴더**, **각 프로젝트의 `.claude/` 설정** | 훅 하나를 고치거나 프로젝트 설정으로 훅을 끄면 장치가 한꺼번에 꺼진다 |
| `.git/hooks`, `.git/config`, `.git/info`(통째가 아니라 이 셋 — `.git/index`·`objects`·`refs`는 커밋이 써야 한다), 서버 쪽 자동 검사 설정 | pre-commit 훅과 push 검사를 끄는 자리 |
| 실행 기록, 원문 기록, 열람 기록 | 검사의 근거 — 고치면 자기신고가 된다 |
| `bench.json`, 이전 케이스 수 파일 | 시험 결과와 "케이스 수가 줄었는지"의 기준 |
| 코드 지문(검토·시험을 마친 시점의 트리 해시) | 커밋 관문이 "지금 코드"에 대한 통과인지 확인하는 기준 |

**설치본은 저장소와 직접 연결하지 않는다.** 장치의 원본은 이 저장소의 `harness/`지만, 설치본은 **버전을 고정한 복사본**이다(저장소를 가리키는 심볼릭 링크 금지 — 링크면 저장소 쪽 파일을 고치는 길이 남는다).
이 저장소를 `/일`로 고치는 날 구현자가 손대는 파일이 바로 자기를 막고 있는 훅이기 때문이다. 보호 폴더에 복사하는 설치 절차는 **AI가 아니라 대표가 본인 터미널에서** 돌린다(AI 쪽은 그 폴더에 쓸 수 없다). 새 버전 설치는
승인 관문을 거친 뒤 점검 스크립트가 등록 상태를 확인할 때만 한다.

## 시험은 샌드박스 밖에서 돈다 — 시험받는 코드가 결과를 못 고치게

bench.json·실행 기록·코드 지문·이전 케이스 수는 보호 파일이라 직원도, 직원이 터미널에서 띄운 시험 스크립트도 쓸 수 없다.
그래서 시험은 직원이 돌리지 않는다. **직원은 실행을 요청만** 하고, 궤도 스크립트(훅)가 **샌드박스 밖에서** 시험을 띄운다.
시험받는 코드(구현자가 쓴 것)는 다시 **샌드박스 안**에서 돌고, 결과 파일은 그 코드가 끝난 뒤 **별도 단계**가 샌드박스 밖에서
쓴다. 시험받는 코드가 돌면서 bench.json이나 케이스 수 파일을 고치는 길이 없다. 실행 기록과 코드 지문도 같은 방식이다.
훅이 실제로 샌드박스 밖에서 도는지는 「첫 시험에서 확인할 항목」에 있다.

## 시험대·케이스·일지·도면 보호

- **⓪에서 더하는 새 파일 이름은 실행기가 매긴 케이스 번호 형식만** 허용한다. 시험 도구가 자동으로 읽는 이름(예: pytest의
  `conftest.py`)을 새 파일로 넣으면 기존 케이스 전부의 동작을 바꿔 통과시킬 수 있고 케이스 수 감소 검사에도 안 걸리기 때문이다.
- 구현 칸에서 고칠 수 있는 **프로젝트 시험 설정**(`package.json`의 test 줄, jest·pytest 설정)도 같은 길이다. 실행기는 프로젝트
  설정 대신 **하네스 쪽 고정 설정**으로 돌고, 프로젝트 안의 시험 설정 파일은 시험대 보호에 넣는다. 시험 실행기 파일 자체는
  **전역(하네스 설치 폴더)**에 있고 보호 파일이다.
- **도면**(결정 문서)은 보호 파일이다. 도면을 바꾸는 것은 케이스 정리와 한 묶음으로 대표 승인이다.
- **작업 일지는 덧붙이기만** 된다(기존 줄 수정·삭제 불가). 케이스가 근거로 가리키는 곳이기 때문이다.
- `scripts/probe/`의 실측 로그는 **훅이 실제 실행에서 남긴 것만** 인정한다. 직원이 손으로 쓴 로그는 "실측"이 아니다.
- **수동 케이스는 다시 올라온다**: 케이스에 적힌 화면·파일 경로가 바뀐 일에서는 검토자 판정표에 그 수동 케이스 줄이
  자동으로 다시 올라온다. 등록한 뒤 잊히지 않는다.
