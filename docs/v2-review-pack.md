# 1부
# IF 공방 v2 — 장치 상세: 어떻게 막는가

`v2.md`의 궤도 표와 직원 표가 "무엇을 막는가"라면, 이 문서는 "어떻게 막는가"다. 원칙은 하나: **AI가 적은 글을 믿지 않고, 훅이 따로 남긴 기록과 대조한다.**

이 문서는 둘로 나뉜다: 여기(검사·보호 파일)와 `v2-devices-2.md`(시험 케이스 관리 · 상한값·설치 · 막는 훅 목록).

## 장치는 AI의 자기신고를 믿지 않는다

산출물 검사가 "보고서에 어떤 글자가 있는가"에 기대면, 그 글자를 쓰거나 안 쓰는 것만으로 통과된다.
그래서 검사는 AI가 적은 글이 아니라 **훅이 따로 남긴 기록**과 대조한다.

- **보호 파일 목록** — 다음 파일은 모든 직원과 반장의 샌드박스 허용 경로 **밖**에 있어 AI가 쓸 수 없고, 훅만 쓴다:
  일 상태 파일, 설정 파일, 훅 스크립트 폴더·전역 설정·설치 폴더·프로젝트 `.claude/` 설정, 실행 기록, 원문 기록, 열람 기록, `bench.json`, 이전 케이스 수, 코드 지문. 전체 표는 `v2-devices-2.md` 「보호 파일 목록」. 훅 하나를 고치면 장치가 한꺼번에 꺼지므로 고치는 길은 대표 승인 관문 하나뿐이다. 샌드박스는 터미널에만
  걸리는 벽이므로, **쓰기·편집 도구에도 같은 보호 경로 거부 규칙**이 훅으로 따로 걸린다(터미널 없는 사실확정자·계획자·시안자도
  이 파일을 못 쓴다). 설정 파일을 고치는 유일한 길은 대표의 승인 관문이며, 바꾼 날과 이유가 함께 기록된다.
- **실행 기록**: 훅이 일 폴더에 실행된 명령·종료 코드·시각을 자동으로 쌓는다(보호 파일).
  구현 칸의 "핵심 경로를 돌렸다"와 보고의 「실측」 절은 이 기록에 **plan.md가 통과 장면마다 고른 `tests/bench/scenes/` 스크립트**가 글자
  그대로, **종료 코드 0으로**, **마지막 편집보다 뒤에** 있어야 인정된다. 역할은 나뉜다: 계획자는 장면마다 어느 스크립트를 쓸지
  고르기만 하고, 스크립트 **내용**은 시험자가 쓴다(구현자는 둘 다 못 한다). 스크립트가 테스트 실행기를 부르면 실행기가 읽는 설정
  (테스트 범위·제외 목록)도 `tests/bench/` 안에 두거나 보호 목록에 넣는다 — 루트 설정을 구현자가 고쳐 실제로 도는 범위를 줄이는
  길을 막는다. 구현자의 「명령 오류」 표시는 **시험자가 확인해야** 인정되고, ③으로 되돌리는 횟수에도 따로 상한이 있다.
- **칸이 끝날 때 바뀐 파일 검사**: 도구 화이트리스트는 터미널이 열린 칸(실측·구현·검토)에서는 충분하지 않다 —
  터미널로 어떤 파일이든 고칠 수 있다. 그래서 칸이 시작할 때와 끝날 때 작업 폴더의 **해시**(추적 파일 + 새 파일)를
  훅이 비교해 **허용 경로 밖에서 바뀐 파일**을 찾고, 하나라도 있으면 다음 칸을 열지 않고 되돌린다. 검토자 칸에서
  바뀐 파일이 있으면 그 판정은 무효다.
- **터미널로 고치는 길은 샌드박스가 막는다**: 편집 도구를 빼는 것만으로는 부족하다. 벽은 하나 — 터미널이 있는 칸은
  하네스 샌드박스에서 돌아 허용 경로 밖 쓰기가 파일 시스템 단위로 거부된다. 그 뒤에서 ① 훅의 명령 검사(보조),
  ② 칸 끝 해시 비교(확인)가 돈다. 검토자는 **일회용 작업 사본**에서 일한다: 쓰기는 되지만(테스트·빌드·임시 DB가
  디스크에 써야 하므로) 칸이 끝나면 사본을 통째로 버리고, 원본은 해시 비교가 지킨다. 두 가지를 더 정한다 — 판정 근거로
  쓰는 실행 기록은 **사본이 원본과 같은 상태**에서 돌린 것만 인정한다 — 비교 범위는 칸 끝 해시 비교와 같다(추적 파일 + 새
  파일: 의존성 폴더·잠금 파일·환경 파일·테스트 실행기 설정까지, "소스"만이 아니다). 검토자가 사본에서 무엇이든 고친 뒤 돌린
  기록은 무효다. 사본에는 **운영 키가 들어가지 않는다**(테스트 키만) — 사본을 버려도 외부로 나간 게시·발송은 돌아오지 않기 때문이다.
- **구현자는 소유표 밖을 못 고친다**: "자기 파일만"은 지시가 아니라 훅이 plan.md의 파일 소유표를 읽어 편집 도구를
  막는다. 주인 없는 공용 파일(설정, DB 구조, 패키지 목록, 공용 타입)은 ③ 계획 칸에서 한 사람에게 배정해야 계획이
  통과되고, 배정되지 않은 파일이 필요해지면 ③으로 되돌려 소유표를 고치는 것이 보통 길이고, 민감 영역 파일만 대표 승인이다(반장 승인은 쓰지 않는다).
- **대표 원문 인용**: 입력 단계 훅이 대표가 친 메시지를 **원문 기록 파일**에 그대로 쌓는다(AI가 편집할 수 없는 파일).
  시안의 "이거다", 채점표의 대표 선택, 건너뛰기 사유처럼 대표가 말한 것으로 적는 문장은 그 기록과 **글자 그대로**
  맞아야 칸이 열린다. 기록에 없으면 인용이 아니라 AI가 쓴 글이다. (작업 일지가 대표 원문을 저장할 때 쓰는 것과 같은 검사다.)
- **출처도 기록과 대조한다**: 훅이 그 일에서 실제로 열어 본 웹 문서 주소, 곳간 검색 결과, probe 로그를 **열람 기록**으로
  쌓는다. facts.md의 「통과」 줄 출처는 이 열람 기록에 있어야 인정된다 — 칸이 채워졌는지가 아니라, 그 주소를 정말
  열었는지를 본다. 실측 칸과 같은 원리다.
- **실측 칸에는 운영 키가 없다**: "조회·테스트 모드만"을 AI가 판정하면 다시 자기신고다. 그래서 실측 칸에는 테스트
  키·조회 전용 키만 넣어 주고 운영 키는 아예 주지 않는다. 판정할 것이 없다. 운영 키는 **프로젝트 폴더 밖, 직원 샌드박스가 읽을 수 없는 위치**에만 있다(폴더 안 `.env`에 있으면 읽기 도구나 `node -e` 한 줄로 실제 게시·결제를 부를 수 있다 — 경로 거부 규칙은 쓰기를 막는 장치라 이 길은 못 막는다). 구현자·검토자 샌드박스는 외부 통신을 막거나 허용한 주소만 연다. 검토자의 일회용 사본에는 `.env`를 복사하지 않는다. 승인 관문은 **운영 키를 주는 것이 아니다** —
  승인되면 "테스트 계정으로 쓰기 호출 1회"가 짧은 창(설정값) 동안 열릴 뿐이다. 테스트 키로도 실제 수신자에게 나가는
  서비스(메일·문자)가 있으므로, 수신처는 **정해진 테스트 목록**으로만 둔다(서비스별 동작은 그 서비스 문서로 확인).
- **값 대조는 스크립트가 한다**: probe 로그는 응답 필드를 구조로 남기고, facts.md의 값 표와 그 필드를 **스크립트가**
  대조한다. 다르면 ①로 되돌아가는 것도 스크립트가 정한다.
- **사실확정의 통과 줄**: 「확인 필요」를 0개로 만드는 것만으로는 열리지 않는다. 「통과」 줄마다 출처가 있어야
  하고, 외부 값은 ② 실측의 실제 응답과 대조해 다르면 되돌아온다. 표에서 값을 빼는 것은 "코드에 넣지 않음"이므로,
  구현 칸에서 facts.md에 없는 값을 쓰면 검토자가 불통과로 잡는다.
- **소형 궤도 재판정**: 승격 조건은 계획서의 파일 수로 한 번, ⑤가 끝날 때 **실제로 바뀐 파일 수와 경로**로 한 번
  더 본다. 두 번째에서 넘으면 소형으로 끝내지 못하고 전체 궤도의 남은 칸을 지난다.
- **파일 소유 겹침**: ③ 계획 칸이 구현자들의 소유 범위가 겹치는지 코드로 검사하고, 겹치면 계획이 통과되지
  않는다. 여러 명이 함께 건드리게 되는 파일(설정, 패키지 목록, 공용 타입)은 반드시 **구현자 한 명**에게 배정해야 계획이 통과된다. 배정되지 않은 파일이 구현 중에 필요해지면 두 길뿐이다: ③ 계획 칸으로 되돌려 소유표를 고치거나(보통 길, 코드가 허용), 민감 영역 파일이면 대표 승인(`승인 <이름>`). 반장 승인은 AI가 AI에게 주는 승인이라 쓰지 않는다.
- **시험 결과와 코드 지문**: `bench.json`은 보호 파일이라 시험 스크립트만 쓴다(`scripts/probe/`의 스크립트도 못 쓴다). 검토와
  시험을 마친 시점에 **코드 지문**(`git write-tree`로 뽑은 트리 해시 — 코드가 조금만 달라도 값이 바뀐다)을 review.md와 bench.json에
  남기고, 커밋 관문은 지금 올라갈 코드의 지문과 같을 때만 연다. 검토 뒤 한 줄이라도 고치면 ⑥으로 되돌아간다.
  구현 칸에서는 `tests/bench/`를 편집할 수 없다 — 테스트를 약하게 고쳐 통과시키는 길을 막는다.
- **실측의 안전**: 실측 호출은 조회·테스트 모드만이다. 한 번 부르면 진짜 일이 일어나는 호출(게시·발송·결제·삭제)은
  테스트 계정·테스트 수신처로만, 승인 관문을 지나 짧은 창 동안 1회 — 운영 키는 어떤 승인으로도 실측 칸에 들어오지 않는다.
- **같은 계열이 같이 놓치는 것**: 구현자와 검토자가 같은 계열이라 같은 실수를 같이 놓칠 수 있다. 고위험 일 외에도
  **검토 불통과가 두 바퀴 연속이면** 다른 계열 점검을 한 번 자동으로 넣는다.
- **교차 점검이 갈릴 때**: 검토자는 통과, 다른 모델 계열은 문제 제기인 경우 — 심각도 상(P0·P1)이면 대표를 거치지
  않고 구현 칸으로 자동으로 되돌리고, 하(P2·P3)이면 기록하고 보고에 표시한다. 「통과/불통과」 판정 자체가 갈리면
  멈추고 대표에게 올린다.
- **지적에는 번호가 있다**: 검토자의 지적은 번호를 달고 바퀴를 넘어 이어진다. 다음 바퀴의 검토자는 이전 번호
  목록을 받아 각 지적에 "이전 번호" 또는 "새 번호"를 붙여야 하고, 그것이 없는 판정은 무효다. 멈출 조건의
  "같은 지적이 남음"은 사람의 느낌이 아니라 이 번호로 센다 — 표현만 바꾼 지적이 새 지적으로 잡혀 상한을 피해
  가지 못한다.

# IF 공방 v2 — 장치 상세 2: 케이스 관리 · 상한값 · 막는 훅

앞부분은 `v2-devices.md`. 읽는 순서는 `v2.md` 맨 위 표.

## 울타리 — 막는 훅

| 훅 | 언제 | 무엇을 막나 |
|---|---|---|
| 일 시작·닫기 | `/일 <이름>` · `일 닫기 <이름> <사유>` | 이미 열린 일이 있으면 두 번째 일 폴더 생성 차단. 열린 동안 들어온 대표 지적은 작업 일지에 「대기」로 적고, 지금 일이 닫히면 반장이 그 지적으로 ⓪ 일을 연다. 비정상 종료로 열린 채 남은 일은 **대표만** 사유를 적어 닫는다 |
| 편집 | 편집·쓰기 | 소스 폴더는 ⑤ 칸에서 소유표 안만. `scripts/probe/`는 ② 칸의 실측자만. `tests/bench/`는 둘로 나뉜다 — 케이스 본체는 **시험자 ∧ ⓪ 칸 ∧ 새 파일**일 때만(번호는 실행기가 자동 부여), `tests/bench/scenes/`(통과 장면 스크립트)는 **시험자 ∧ (③ 칸 또는 「명령 오류」 되돌림 중)**일 때 생성·수정 허용, 고친 이력은 review.md 대조 항목. 보호 파일은 누구도 못 씀 |
| 커밋 | 커밋(글자가 아니라 git 자체의 **pre-commit 훅**에도 같은 검사) | review.md 통과 + bench.json pass **+ 두 파일에 적힌 코드 지문(트리 해시)이 지금 올라갈 코드의 지문과 같을 것**. 다르면 ⑥으로. bench.json은 커밋 훅이 믿지 않고, 지문이 없으면 그 자리에서 시험을 다시 돌린다 |
| 배포 | 배포 스크립트, 그리고 main push로 배포가 자동 실행되는 프로젝트는 **push 훅**에도 | ⑥⑦ 산출물 + 코드 지문 일치 + 교차 점검 결과 도착 전엔 차단 |
| 작업조 | 작업조 생성 | ⑤⑥ 칸에서 역할 직원이 아닌 범용 작업조 차단 |
| 상태 줄 | 답이 끝날 때 | 금지어 검사는 쓰지 않는다("끝났습니다"로 피해 간다). 일이 열려 있으면 훅이 답 끝에 **"현재 칸 ④ · 미검증"** 같은 상태 줄을 자동으로 붙인다 — 어떤 표현을 쓰든 실제 상태가 같이 보인다 |
| 반장 터미널 | 일이 열린 동안 | 반장의 터미널 명령 전부 차단, 호출 수 초과 시 차단("새 창" 안내) |
| 터미널 | 직원의 터미널 명령 | 금지 목록이 아니라 **허용 목록**(화이트리스트)에 있는 명령만 통과(`python -c`·`node -e`·`perl -i`·`git checkout <파일>`·`git apply`·`curl -o` 같은 우회는 목록에 없으므로 막힘). 명령이 끝나면 `git status`로 허용 경로 밖 변경을 보고, 있으면 되돌린 뒤 막는다. 벽은 샌드박스 |
| 공개 저장소 push | `git push` | 금지 목록(빌려온 이름·사람 이름·내부 주소·경로·메일·계정명·날짜·일지 번호·승인 예시)에 걸리면 차단 |
| 시험대 보호 | 편집·쓰기 | 구현 칸에서 `tests/bench/` 편집 차단, `bench.json` 직접 쓰기 차단(시험 스크립트만 씀) |
| 승인 범위 | `승인 <이름>` | 이름이 열린 일·프로젝트와 맞지 않으면 거절하고 다시 입력받음. 배포·삭제는 짧은 창을 따로 둠(설정값) |
| v1 유지 | — | 승인 관문(`승인 <이름>`), 위험 명령, 비밀 파일, 훅 자체 보호 |

- 임계값과 민감 영역 패턴은 훅이 읽는 **설정 파일**에 둔다. 고치는 것은 승인 관문이다(아래 「보호 파일 목록」).
- 일 폴더가 열려 있지 않으면 v2 훅은 **아무것도 하지 않는다** → 다른 세션·다른 프로젝트는 `/일`을
  쓰기 전까지 영향이 없다. 되돌리기는 설정에서 훅 몇 줄을 빼는 것이다.

## 시험 케이스는 쌓기만 하지 않는다

- 케이스마다 **어느 지적에서 나왔는지**(작업 일지 번호)와 **어느 기준(도면)에 묶이는지**를 적는다.
- 도면이 바뀌어 더는 맞지 않는 케이스는 그 자리에서 정리한다(기준 변경 보고에 "정리한 케이스" 칸).
- 결과가 들쭉날쭉한 케이스는 「불안정」으로 표시한다: **통과 수에서는 빼되 ⑦은 막는다.** 따로 고친다. **불안정 판정은 사람도 AI도 하지 않는다** —
  시험 스크립트가 같은 코드로 여러 번(설정값, 처음 값 5회) 다시 돌려 결과가 갈릴 때만 붙이고, 불안정으로 넘어간 케이스 수는 보고에
  반드시 찍힌다. **불안정은 통과가 아니다** — 불안정 케이스가 하나라도 있으면 ⑦은 열리지 않고, 고쳐서 안정이 되거나
  대표가 그 케이스를 따로 판단해야 한다(면제에는 날짜와 유효 기한을 적는다 — 예: 다음 일까지. 영구 면제는 없다). 구현자는 `tests/bench/`를 못 고치므로 **불안정 판정이 나면 시험자에게 넘어간다** —
  원인이 시험 스크립트 쪽이면 시험자가 고치고, 코드 쪽이면 시험자가 재현 조건을 케이스에 적어 구현 칸으로 보낸다. 가끔만 터지는 진짜 버그가 불안정 뒤에 숨는 것을 막는다.
- **케이스 수가 줄면 실패다.** 시험대는 이전 실행의 케이스 수를 기억하고, 수가 줄었으면 pass를 내지 않는다
  (정리한 케이스는 기준 변경 보고에 적힌 것만 예외).
- **지적 → 케이스는 시험자가 ⓪ 시험 등록 칸에서 쓴다.** 대표 지적이 들어오면 반장이 작업 일지에 남기고 **그 지적으로 새 일을 연다.**
  그 일의 첫 칸이 ⓪ 시험 등록이다: 시험자가 케이스를 쓰고 **현재 코드에서 실패하는 실행 기록**을 남긴다. 그다음 ①~⑥을 지나
  ⑦에서 통과 기록이 남아야 케이스가 등록된다. 순서는 코드에 고정되어 "두 번째 일 차단"과 꼬이지 않는다(지적 일 하나 = 일 하나).
- **⓪에서는 새 파일만 더할 수 있다.** 기존 케이스를 고치거나 지우는 것은 재발 0이 무너지는 자리라 대표 승인으로만 열린다.
  케이스 번호는 **실행기가 자동으로 매겨** 겹침이 처음부터 생기지 않고, 그래도 겹치면 실패로 처리한다. 이전 케이스 수를 기억하는 파일은 보호 파일이며, **수동 케이스 수가 줄어도** 실패다.
- **자동 시험으로 실패를 재현할 수 없는 지적**(디자인 취향, 문구 느낌)은 ⓪을 영원히 못 빠져나가므로 출구를 둔다: 대표가
  "자동 시험 불가"를 고르면 「수동 케이스」로 등록되고 ⓪은 닫힌다. 수동 케이스는 검토자의 화면 품질 판정표에 줄 하나로
  들어가며, "고치기 전 실패·고친 뒤 통과" 대신 **고치기 전 캡처·고친 뒤 캡처·검토자 판정 줄**을 요구한다. 자동 케이스와
  섞지 않고 수를 따로 센다.
- **케이스는 "고치기 전 실패 · 고친 뒤 통과" 둘 다 확인돼야 등록된다.** 새 케이스를 고치기 전 코드에서 돌려 실제로
  실패하는 것을 실행 기록으로 남기고, 고친 뒤 통과하는 것도 기록으로 남긴다. 둘 중 하나라도 없으면 시험대에 들어가지
  않는다 — 아무것도 못 잡는 케이스가 쌓이는 것을 막는다. 이것이 "재발 0"이 말이 아니라 장치가 되는 지점이다.

## 상한값과 설치는 기록으로 관리한다

- 호출 상한·바퀴 상한·시간 상한·소형 궤도 파일 수는 처음 값이 정답이 아니다(터미널 비율은 상한이 아니라 계기판 지표다). 설정 파일에 **바꾼 날과 이유**를 함께 적고,
  계기판 숫자(막힘이 너무 잦은가, 너무 느슨한가)로 조정한다.
- 설치 뒤에는 읽기 전용 점검 스크립트로 훅이 실제로 등록됐는지 확인한다. 저장소에는 push마다 테스트가 자동으로
  돌게 하여(CI) 울타리 코드 자체가 망가지는 것을 막는다.


**역할을 무엇으로 구분하나.** 반장 터미널·작업조·터미널 훅은 "누가 명령했는지"를 알아야 작동한다. 훅 입력에 직원 식별이
들어오는지 첫 시험에서 확인하고, 들어오지 않으면 **직원마다 별도 작업 사본(폴더)**을 주어 경로로 역할을 구분한다(경로 = 역할).
확인되기 전까지 역할별 훅 세 개는 "추정"으로 표시한다.

## 보호 파일 목록 — AI가 쓸 수 없고 훅·궤도 스크립트만 쓴다

쓰기·편집 도구와 샌드박스 양쪽에 같은 거부 규칙이 걸린다. 고치는 길은 **대표 승인 관문 하나**뿐이고, 바꾼 날과 이유가 기록된다.

| 파일 | 왜 보호하나 |
|---|---|
| 일 상태 파일(열린 일, 현재 칸, 건너뜀 기록) | 칸 숫자를 바꾸거나 표시를 지우면 울타리 전체가 꺼진다. **칸 이동과 일 닫기는 궤도 스크립트만** 하고, 앞 칸 산출물을 확인한 뒤에만 넘어간다 |
| 설정 파일(임계값·민감 영역 패턴·경고/차단 모드) | 느슨하게 고치면 모든 관문이 느슨해진다 |
| 훅 스크립트 폴더, 훅을 등록하는 **전역 설정 파일**, **하네스 설치 폴더**, **각 프로젝트의 `.claude/` 설정** | 훅 하나를 고치거나 프로젝트 설정으로 훅을 끄면 장치가 한꺼번에 꺼진다 |
| 실행 기록, 원문 기록, 열람 기록 | 검사의 근거 — 고치면 자기신고가 된다 |
| `bench.json`, 이전 케이스 수 파일 | 시험 결과와 "케이스 수가 줄었는지"의 기준 |
| 코드 지문(검토·시험을 마친 시점의 트리 해시) | 커밋 관문이 "지금 코드"에 대한 통과인지 확인하는 기준 |

**설치본은 저장소와 직접 연결하지 않는다.** 장치의 원본은 이 저장소의 `harness/`지만, 설치본은 **버전을 고정한 복사본**이다.
이 저장소를 `/일`로 고치는 날 구현자가 손대는 파일이 바로 자기를 막고 있는 훅이기 때문이다. 새 버전 설치는 승인 관문을 거친 뒤
점검 스크립트가 등록 상태를 확인할 때만 한다.

## 모든 개발에서 먹히게 — 장치는 전역, 데이터만 프로젝트

| 전역(하네스 홈, 이 저장소의 `harness/`) | 프로젝트 안(데이터) |
|---|---|
| 막는 훅과 설정 파일 | `tests/bench/` 시험 케이스 |
| 스킬(크래시 아웃·아우라 파밍·육칠·화면 품질 점검·계획 쓰기…) | `scripts/probe/` 실측 로그 |
| AI 직원 7명(⓪~⑥) 파일 | 도면(결정 문서) |
| 궤도 스크립트, `/일` 명령 | 프로젝트 안내 한 줄 |
| 공통 규칙 2장(안전 + 이 문서) 자동 로드 | 미리보기 스크립트(템플릿에서 생성) |

- 설치: 저장소를 받아 설치 절차 한 번 → 다른 컴퓨터에도 같은 훅·스킬·직원·명령.
- `/일 <이름> 루트=<폴더> [소형] [화면]`: 어느 폴더든 처음이면 `tests/bench/`·`scripts/probe/`·도면을
  만들고 프로젝트 목록에 등록한다. 그 순간부터 같은 궤도다.
- **자동으로 읽히는 절차 문서는 두 장**(안전 규칙 + 궤도 요약)으로 유지한다. v2 문서 여섯 개는 설계 문서라 자동으로 읽히지
  않는다. 자동 로드 문서가 늘어나면 실패 신호다.
  "이 프로젝트에서만"이라는 말이 설계에 나오면 설계가 틀린 것이다.

## 한계 → 돌파 장치 → 그래도 남는 것

| 한계 | 돌파 장치 | 남는 것 |
|---|---|---|
| AI는 글로 적은 규칙을 안 지킨다 | 지킬 필요가 없게: 스킬 주입, 도구 화이트리스트, 순서는 코드 | 화이트리스트 안의 엉뚱한 선택 → 검토자·시험대 |
| 자료 안 보고 짐작 | 출처 없는 값 반입 차단, 실측 없이는 구현 칸 안 열림, 원문표 주입 | 출처를 잘못 읽는 경우 → 결과로 잡음 |
| 판단 오류 자체 | 육칠, 두 모델 계열 교차 판정(둘이 다르면 대표), 테스트 먼저, 지적→케이스 | **처음 보는 오류 1회** |
| 문맥 폭발 | 반장 호출 상한, 칸마다 새 문맥, 일 하나 = 창 하나 | 계기판 "반장 호출 수"·"토큰"으로 확인(시험 전) |
| "완료"를 쉽게 말함 | 답 끝에 상태 줄 자동 부착, 「미검증」은 막힘 | 계기판 "「미검증」 수용"으로 확인(시험 전) |
| 검증이 많고 못 믿음 | 검토 1 + 시험대 1, 교차 점검 1회 상한 | 새 기능 첫 회는 케이스가 없음 → 그때 만듦 |
| 화면을 숫자만 맞춤 | 캡처 옆 시안·"이거다" 관문·포트폴리오 판정 | 대표 취향은 "이거다"로만 |
| 같은 설명 반복 | 직원 파일 고정, 원문표 한 곳 | 계기판 "대표 메시지 수"로 확인(시험 전) |
| 워크플로를 켜야 함 | `/일` 자체가 승인 | 일 시작 훅이 실제로 막는지 첫 시험에서 확인 |
| 설정을 AI가 못 바꿈 | 관문 한 번, 임계값은 설정 파일 | 훅 수정은 관문(그대로가 맞음) |
| 느리고 비쌈 | 소형 궤도, 칸별 모델 등급, 동시 실행, 칸에 파일만 전달 | 첫 시험의 측정 비용 |
| 실패가 흩어져 안 보임 | 멈춘 자동화 보드(아래) | 보드는 다음 단계 |
| 칸 사이 전달 품질(파일뿐) | 산출물 형식 고정 + 검토자가 통과 장면으로 대조 | 시험으로 재는 것 |

진짜 남는 것은 둘이다. 처음 보는 오류의 첫 1회, 그리고 칸 사이 전달 품질. 전자는 미리보기와
케이스화로 두 번째를 없애고, 후자는 시험으로 숫자로 확인한다.

## 다음 목적지 — AI 사무실

궤도 위에 **보는 창과 상시 직원**을 얹는다. 궤도 없이 사무실만 만들면 예쁜 화면 뒤에서 같은 일이
반복된다.

| 사무실 요소 | 우리 장치 |
|---|---|
| 비서실장 | 반장 = `/일` 시작·결과 전달 |
| 조직도·AI 직원 | 직원 7명(⓪~⑥) + 프로젝트 운영 직원(경보 처리) |
| 지금 도는 일 | 열린 일 폴더 목록 + 칸 위치 |
| 멈춘 자동화 보드 | 모든 프로젝트의 실패·경보·승인 대기를 한 화면에 한 줄씩, 고치기·기록 보기, 휴대폰 알림 |
| 승인함 | 관문 요청·"이거다"·채점표 선택을 한 곳에 |
| 회의실 "생긴 규칙" 카드 | 작업 일지 자동 카드 + "승격" 버튼 → 도면 |
| 상시 직원 | 시험대 야간 실행 + 경보 처리 직원. 실행 틀(대기열·무인 실행·권한 울타리)이 먼저 |

## 이 저장소의 상태

- 들어 있음: v1 울타리 훅(승인 관문·위험 명령·완료 검증·착수 보고), 작업 일지 저장, 설정·설치 안내, 테스트.
- 이 문서: v2 설계. 궤도 엔진·직원 파일·궤도 스크립트·시험대 틀은 **실제 시험을 통과한 뒤** `harness/`로
  들어온다. 돌려 보지 않은 코드는 올리지 않는다.

## 켜는 순서 — 경고 모드에서 차단으로

새 훅은 처음 며칠 **경고 모드**로 돌린다: 막지 않고 "막았을 것"을 계기판에 헛막힘 수로 센다. 헛막힘이 잦은 훅(공개 push 금지
목록, 터미널 허용 목록이 가장 많이 걸릴 자리)은 목록을 고친 뒤 **차단 모드**로 바꾼다. 모드 값은 보호된 설정 파일에 있다.

CI(push마다 자동으로 도는 테스트)에는 "막혀야 하는 명령 목록"을 실제 훅에 넣어 정말 차단되는지 보는 시험을 둔다. 목록 첫
줄은 터미널 우회 명령들(`python -c`, `node -e`, `perl -i`, `git checkout <파일>`, `git apply`, `curl -o`)이다. 설치 점검은
설치 직후 한 번이 아니라 **세션을 시작할 때마다** 등록 상태를 한 줄로 보여 준다.

## 공개 저장소 push 검사와 라이선스 고지

빌려온 이름은 금지 목록에 있지만 BSD-3·MIT는 **고지를 남기는 것이 조건**인 라이선스다. 고지 문구가 들어 있는 파일
(`THIRD_PARTY_NOTICES.md`와 해당 스킬의 출처 문서)은 검사의 **예외로 등록**한다 — 고지를 지워 라이선스를 어기거나 push가
막히는 일이 없게. MIT 원본(크래시 아웃·육칠·아우라 파밍)의 고지도 그 파일에 둔다. 검사 범위는 마지막 상태만이 아니라 **이번에
올라가는 커밋 전부**다(지운 내용도 기록에 남는다). 날짜 패턴은 잠금 파일·변경 기록에 계속 걸리므로 작업 일지에 쓰는 날짜
형식으로만 좁힌다.
