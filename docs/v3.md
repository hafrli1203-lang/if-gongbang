# v3 — worktree tools (design)

v3 is a small set of shell/Python tools (`tools/`) that give an agent or a person an isolated,
disposable work copy of a git-tracked app, run commands and a dev server inside it safely, and
either land the change on the app's default branch and deploy it, or clean it up — without ever
touching the production checkout, the production database, or another copy's state.

This replaces running an agent directly against the production checkout: edits, a half-finished
`npm install`, or a crashed dev server in the production folder are now contained to one
disposable copy per job. It supersedes an earlier design (kept here as `v2/`, now archival —
see the top of that folder's own README) built around a stricter execution gate; v3 is a
lighter, filesystem-and-scope-check-based approach, with a correspondingly different and
smaller guarantee (§ "What this is not" below).

## Where a chat-style front door fits in

A person can also hand a task to a chat-style "office" app (a front door that turns a plain
request into a dispatched session, shows its progress, and surfaces anything that needs a
decision) instead of typing commands directly. That front door is not a separate pipeline with
its own rules — it is one more entry point onto the same tools described here: it still starts
a disposable work copy (`wt-new.sh`), runs the job inside it (`wt-run.sh`), and lands/deploys
through the same scope-checked path (`wt-land.sh`). The guarantees and limits in this document
(§ "What this is not") apply to work started this way exactly as they apply to work started
from a terminal - a nicer entry point does not grant it a stronger one.

## The pieces

1. **A work copy** (`wt-new.sh`) — a `git worktree` on its own branch, its own free TCP port,
   its own Postgres test-database slot (schema wiped and re-migrated, never the production
   database), and its own `node_modules` (hard-link copy of the app's, so installing inside a
   copy never touches the app's real packages — `wt-bin/`'s `npm`/`pnpm`/`yarn` wrappers refuse
   install-type subcommands with a clear message instead).
2. **Running something inside it** (`wt-run.sh`) — one command, or the app's dev server, inside
   a memory-capped `systemd --user` scope, with an environment built from an allow-list (see
   docs/v3-adapters.md "환경") so a parent session's own credentials and a production database
   address never reach the copy.
3. **A scope fence** (`scope-check.sh`, `.wt.scope`) — before anything lands, the files the copy
   actually changed are compared against a list of allowed path globs written when the copy was
   made. `package.json`, lock files and `migrations/`/`drizzle/` paths only pass when the scope
   file names them explicitly — a broad `**` does not cover them. This is a **cooperating-agent
   fence**, not a sandbox boundary (see "What this is not" below).
4. **Landing** (`wt-land.sh`) — rebase onto the app's current default branch, scope-check, an
   empty "land" commit recording who landed it, fast-forward merge into the app folder, then
   deploy through the configured deploy adapter (docs/v3-adapters.md). A failed deploy reverts
   the source and restarts the previous build/workers automatically; a successful one pushes
   and marks the copy done. `--dry` runs every check for real and reports what it would do
   without changing anything.
5. **Cleanup** (`wt-gc.sh`) — removes only copies that are actually finished: marked done, or
   stale *and* confirmed abandoned by an external task-status adapter (docs/v3-adapters.md) —
   never by inferring "probably done" from idle time alone.
6. **Verification** (`verify/example/`) — a template for an app's own `verify-<app>` skill:
   launch the copy, a read-only health check ("doctor"), drive one real user journey, capture
   proof (screenshots, DOM snapshot, DB rows). `wt-land.sh` runs this automatically after a
   successful deploy when the app has one.

## What this is not

- **Not a sandbox.** `.wt.scope` and `.wt.json` live *inside* the work copy. A cooperating
  agent that respects them gets a clean, enforced lane; an adversarial one with shell access
  inside the copy can edit them. Treat this as a workflow fence for an agent following
  instructions, not as isolation from a hostile process. A stronger boundary needs the allowed
  scope and base commit checked against a record kept *outside* the copy by whatever is
  dispatching jobs.
- **Not a full CI gate.** v3's own checks are scope and path shaped. Build, lint, test and
  review are the deploy adapter's job (docs/v3-adapters.md) — v3 does not run them itself.
- **Not a guarantee carried over from v2.** v2 (archival, `v2/`) enforced scope through an
  execution gate and sandbox before a step ran; v3 checks the paths a copy touched *after the
  fact*, against the same kind of scope file. The two are not interchangeable protections, and
  a scope-compliance result measured against v2's gate does not transfer to v3 — see
  docs/v3-walkthrough.md for what has actually been measured against v3 itself (one unit, not a
  general claim).

## The full automation pipeline (hooks + tools, not only the worktree scripts)

The six pieces above are what runs an agent's job inside one disposable copy. Three more
layers run around every job, independent of which app or which agent session is doing the
work: a set of PreToolUse hooks that gate the *session* itself (not only the final land), the
landing pipeline's own security and reliability checks, and two always-on review tools that
watch every copy across every app.

1. **A copy is made** (`wt-new.sh`), then **a session runs inside it**. From the first command,
   five hooks are active for that session (installed by `hooks/apply_hooks_v3.sh`, registered
   in `settings.json`'s `PreToolUse` block):
   - `hooks/block_dangerous.py` — hard-blocks a structurally destructive command (`rm -rf` on a
     a filesystem root, a home directory, a wildcard, or an unexpanded variable, `git push
     --force`, `git reset --hard`,
     `pkill`/`killall`, a secret-value `echo`, …) by parsing the actual shell grammar (command-
     runner prefix chains, option reordering, nested substitution), not a plain substring match
     — and separately hard-blocks `git rebase`/`reset`/`checkout`/`stash` aimed at *any* work
     copy from *any* session, including that copy's own, so a session cannot discard another
     crew's uncommitted work by cd-ing into their copy.
   - `hooks/protect_sensitive_files.py` — denies read/write access to secret-shaped files
     (`.env*`, `*.pem`, `*.key`, …), to a copy's own `.wt.json`/`.wt.scope`/`.wt.done` state
     files (only `wt-*.sh` may write those), and to another app's source tree from inside a
     copy whose scope does not name it.
   - `hooks/scope_fence.py` — the realtime half of scope enforcement: every `Edit`/`Write`/
     `Bash`/`Agent` call inside a copy is checked against `.wt.scope` *before* it runs, so a
     violation never lands in a commit in the first place (`scope-check.sh`, run again at
     `wt-land.sh`, is the after-the-fact backstop for anything this hook's heuristics miss).
   - `hooks/mcp_scope_limit.py` — inside a work copy, an MCP server call to an owner-linked
     account tool (mail, calendar, drive, …) is denied; those tools are for the person, not for
     an agent working unattended inside a disposable copy.
   - `hooks/merge_settings_hooks.py` — not a PreToolUse hook itself, but the safety check an
     install/upgrade script runs before writing a new `settings.json`: refuses to merge if doing
     so would silently drop an existing hook registration or permission entry.
2. **Before a land, two more checks run that are not about file scope at all:**
   - `sec-gate.sh` audits a Node project's dependency changes from the *commits* being landed
     (never a working folder someone could have hand-edited around), so a compromised or
     typosquatted package addition is caught before it reaches the app's `node_modules`.
   - `suite-check.py` / `harness/suite_trust.py` catch a test suite that silently ran zero
     tests, or whose passing count dropped sharply from its own recorded baseline — the
     "unstable test" detection re-runs only the files that failed, twice more, before deciding
     a failure is real rather than flaky, so a land is not blocked (or wrongly allowed through)
     by one noisy test.
3. **Landing** (`wt-land.sh`) rebases, scope-checks, merges, then deploys. An app with its own
   `DEPLOY_CMD` (self-deploy) goes through the same path end to end, with one extra
   independent confirmation step and its own revert-and-retry-once recovery on failure — see
   docs/v3-wt-interface.md's `wt-land.sh` section and exit code 10.
4. **Every deploy outcome is recorded, not just logged** — `v3/tools/receipts.py` judges a
   deploy's survival from boot/start timestamps (did the unit the deploy touched actually
   restart and stay up, not merely "did the script exit 0") and `wt-land.sh`/`wt-gc.sh` both
   read that record back before treating a copy as safely done.
5. **Cleanup** (`wt-gc.sh`) only removes a copy once it is confirmed finished one of several
   ways (`.wt.done`, a confirmed-abandoned task, or a verifiably merged-and-clean branch even
   without `.wt.done` — see docs/v3-wt-interface.md) — never by idle time alone.

**Two tools watch the whole workspace, independent of any one job:**
- `tools/stall_watch.py` — reads every copy's own task-status adapter (docs/v3-adapters.md) and
  flags one that has gone quiet (no file activity, no unit restart) well past a normal working
  pause, as a table, so a stalled job gets a person's attention instead of silently occupying a
  slot indefinitely.
- `tools/daily_review.py` — a nightly pass over the same task-status source, surfacing the
  *shape* of recent trouble (tasks a person had to redirect, a report missing its required
  parts, an unusually long run, a retry) as a short ranked list, not a line-by-line log — meant
  to catch a recurring process problem, not any single job's outcome.

## Newer pieces

- **Subfolder apps** — `wt-new.sh`/`wt-land.sh`/`deploy.sh` all read `deploy.env`'s `APP_DIR`
  when a repo's actual Next.js project root is a subfolder rather than the repo root (a
  monorepo-shaped app with its web app under e.g. `web/`). A work copy still gets the whole
  repo; the project-root-relative steps (install, dev server, build, next's own
  `tsconfig.json`/`next-env.d.ts` rewrites) run inside `APP_DIR` instead of the copy's top
  level. Absent or empty `APP_DIR` keeps the previous repo-root behavior unchanged.
- **Waiting on a person** (`wt-hold.sh`) — marks a work copy as waiting on something only a
  person can supply (an answer, a QR scan, a decision) by writing `.wt.hold` with a reason.
  `tools/stall_watch.py` then reports it as "waiting", not "stalled", and never pages about it;
  `wt-gc.sh` still only removes it once it is otherwise confirmed finished (uncommitted or
  ahead-of-base work is untouched either way). `wt-hold.sh <app> <name> --release` clears the
  mark.
- **Plain-language alerts** (`v3/tools/notify-text.mjs`) — helpers used by the notification
  path to keep an alert to a non-technical reader in three parts (what happened / why it
  matters / what to do), within each channel's own length limit, and to flag an alert that
  still reads like a raw log line (a file path, an exit code, an unexplained English term) so
  that gap gets fixed at the source rather than silently repeated.

## Skills install list

`install/skills-manifest.json` + `install/install-skills.sh` re-register, on a new machine,
only the plugin marketplaces this install actually uses that have a checked public git/GitHub
origin (a marketplace registered locally from a directory with no git remote has no public
address to record, and is left out rather than copied in as code) and install/enable the exact
plugins this install has enabled from them. A skill built from this workspace's own private
material, or an automatic skill-selection router still being built separately, is reserved in
the manifest's `skill_router` key but not included until it has its own public extraction.
