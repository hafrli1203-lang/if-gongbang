`docs/v2.md`의 설계를 코드로 옮긴 엔진이다. SQLite 장부 하나와 처리기 하나가 상태·권한·요청·승인·증거·복구를
집행하고, AI 작업자는 정해진 칸 하나만 맡는다. 작업자의 말은 믿지 않는다. 바뀐 파일은 사본의 git 상태로, 통과는
처리기가 직접 돌린 시험과 지문으로 판정한다.

## 한 건이 지나는 길

```
열기 → 빌드(작업자) → 합치기 → 검수(다른 모델 계열, 읽기 전용) + 시험대 → 커밋 → 보고 → 닫기 → (발행)
```

- **빌드:** 작업자는 자기 사본 안에서만 읽고 쓴다. 모든 도구 호출은 관문 훅(`engine/gate.py`)이 정책으로 판정한다.
  쓰기는 설정된 경로 접두어 안만, 터미널 명령은 설정된 정규식에 맞는 것만 허용된다.
- **OS 샌드박스:** 작업자·검수자·시험대 프로세스는 bubblewrap으로 감싼다. 장부·비밀 폴더·다른 프로젝트는 보이지 않고,
  관문은 엔진이 미리 써 둔 읽기 전용 사실 파일로 판정한다.
- **합치기:** 사본의 바뀐 파일 중 허용 경로 안의 것만 저장소에 옮긴다. 기준 커밋에서 목적지가 바뀌었으면 멈춘다.
- **검수:** 다른 모델 계열이 읽기 전용으로 diff를 본다. P0·P1이 있으면 멈춘다.
- **시험대:** 프로젝트 시험을 돌리고, 일부러 실패하는 음성 대조 시험이 실제로 실패하는지까지 확인한다
  (항상 통과하는 채점기를 막는다).
- **커밋:** 검수·시험대·지문 세 증거가 같은 트리를 가리킬 때만 커밋한다.
- **발행:** 승인(회차·행동·대상·해시·만료)이 묶인 경우에만, 커밋 해시를 다시 확인한 뒤 배포 명령을 부른다.
  dry-run을 먼저 쓴다.
- **멈춤과 복구:** 어느 단계에서 죽어도 단계 일지로 이어 간다. 외부 효과가 응답 전에 끊기면 실패로 단정하지 않고
  `unknown`으로 두고 사람이 확인한다.

## 사람이 하는 일

- 일을 넣는다. 의존성 추가처럼 작업자가 못 하는 일은 작업자가 요청만 남기고, 사람이 내용을 보고 승인해야 들어간다.
- 결과 가지를 보고 합친다. 배포를 승인한다.

## 실행

```
bash tools/install.sh --apps-root <앱 원본 폴더>   # 가상환경, gb2 명령, AI 직원 6명, /일 명령
gb2 new <app> "<만들 앱>"               # 새 앱을 처음부터 궤도로
gb2 change <app> "<바꿀 내용>"          # 기존 앱 수정을 궤도로
gb2 change <app> "<작은 수정>" --small  # 작업 하나짜리 작은 수정(외부 대상이 있으면 일반 궤도로)
gb2 approve-design <app>                # 시안을 사람이 보고 승인(터미널 입력)
gb2 continue <app>                      # 멈춘 곳에서 이어서
gb2 board --out board.html              # 장부를 읽어 만드는 현황판(정적 HTML)
python -m pytest                      # 단위·수락 시험 (실제 AI 호출 없음)
python -m pytest -m live              # 실제 AI 작업자로 도는 시험 (비용 발생)
python -m engine.cli <init|open|run|status|approve|retry-unknown|close> --config <config.json>

# 앱 하나에 붙여 쓰기 (Node·Vitest 앱)
export GB2_APPS_ROOT=<앱 원본들이 있는 폴더> GB2_WORKSPACE=<엔진 작업 폴더>
tools/gb2 init <app> [--with-release]   # 원본은 그대로 두고 작업 가지·작업 트리·설정을 만든다
tools/gb2 run <app> "<할 일>"           # 한 건을 궤도 끝까지 (검수·시험대 동시, 관련 시험 우선)
tools/gb2 diff <app>                     # 결과 확인
tools/gb2 fix <app> ["추가 지시"]         # 검수·시험에서 실패한 일을 이어서 고치기(작업 유지)
tools/gb2 ship <app>                     # 같은 커밋 전체 시험 1회 → 승인 문구 입력 → master 빨리감기 + 배포
tools/gb2 resolve <app>                  # 배포 결과가 불명확할 때 확인 명령으로 보고 사람이 결과를 기록(재배포 안 함)
```

설정 형식과 규칙 전체는 `ENGINE.md`.

## 한계

알려진 남은 문제(다음에 고칠 것):
- 업무 흐름 층은 데이터·외부 연결 층을 직접 부른다(바꿔 끼워야 하는 곳에만 포트를 둔다).
- 작업자가 허용된 명령으로 실행한 코드는 네트워크와 그 작업자의 로그인 파일·MCP 설정 파일에 닿는다(이 호스트는 샌드박스 안의 샌드박스를 허락하지 않는다). 작업자 CLI는 그 패키지 폴더나 실행 파일만 읽기 전용으로 보인다.
- 수락 장면은 장면마다 새 스냅숏에서 돌고, 추적 파일은 읽기 전용이다. 샌드박스 없이(`sandbox: none`) 돌리면 같은 사용자가 파일을 지우고 새로 쓰는 것까지는 막지 못한다.
- 작업을 새로 시작해 첫 기록을 남기기 전에 끊기면 이어 갈 기록이 없다. 아무것도 시작되지 않은 상태이므로 같은 `gb2 new`/`gb2 change`를 다시 실행한다.
- 배포 호출이 시작됐는데 배포기 영수증이 남기 전에 끊기면 `gb2 continue`가 같은 요청을 이어 가고, `gb2 resolve`도 결과 불명으로 받아 사람이 판정한다(다시 배포하지 않음).
- 실측 통과는 출력의 `PROBE OK <대상 주소>` 줄로 판정한다. 스크립트가 그 주소에 실제로 닿았는지는 따로 증명하지 않는다.
- 수락 사본의 최상위 폴더는 쓰기 가능하다(추적 파일·폴더는 읽기 전용). 시험이 0개 실행됐는지는 Vitest 출력만 알아본다.
- 배포 결과물 지문 대조는 `release.verify_cmd`를 설정했을 때만 한다. 없으면 영수증에 확인 안 됨(verified=false)으로 남는다.
- Python 의존성 감사는 pip-audit가 설치되어 있을 때만 돈다. 없으면 "확인 불가"로 배포 전에 멈춘다.
- 통합 시험(T3, T4, T5)은 실제 gb2 명령·Node 템플릿·엔진 전체·실제 첫 의존성 설치를 돌리지만 AI 작업자·배포는 대역이다. 실제 AI로 새 앱을 끝까지 만든 기록은 아직 없다.

- 같은 사용자 권한으로 도는 작업자가 실행하는 코드는 샌드박스가 보여 주는 범위를 정책 검사 없이 읽는다.
  관문이 남기는 판정 로그는 감사 기록일 뿐이고, 집행은 훅의 종료 결과로 한다.
- 프로세스를 세션에서 떼어 내는 자손은 프로세스 그룹 종료로 못 잡는다(cgroup 미사용).
- 실제 프로젝트 적용은 Node(Next.js·vitest) 기준으로 확인했다. 새 앱 골격의 화면 파일은 파일·스크립트·소유 경로까지만 시험하고, 브라우저로 띄워 쓰는 시험은 아직 없다.
- 현황판은 처리 흐름이 남긴 최종 결정을 보여 주는 화면이다. 인증서를 따로 검증하지 않는다.
