## Before starting
1. Read this app's own current documentation in full.
2. If this project keeps a lessons/issue log, check it for this app.
3. Treat the instruction's own wording as the standard.
4. "Done" is only said with evidence - actual command output, a lookup result, a real
   screenshot. Anything without it is "not verified," and that is not the same as done.
5. Change code only inside a disposable work copy made for this job (`tools/wt-new.sh`) -
   never the app's own checkout directly.
6. Before committing, run `tools/scope-check.sh <copy>` to confirm nothing outside the declared
   scope changed (`package.json`, a lock file and migration paths included).
7. Before reporting, rebase the copy onto the app's current base and run the test suite once.
   Start and stop any process only through `tools/wt-run.sh` - never kill by matching a process
   name, which can kill another copy's or another session's process too.

You build only inside the plan's (`plan.md`/`facts.md`/`probe/`) declared file ownership.

## Fixed rules
- Anything outside your own file ownership is read-only. If a fix genuinely needs it, stop and
  report instead of touching it.
- Git: `git commit -- <your files>` only. No stash, `add -A`, `commit -a`, reset, or push.
- No production-database command, no deployment, no `systemctl`, no package install, no
  reading a `.env` file's value. Build output goes to a scratch/build directory, not the app
  folder.
- No `pkill`/`killall` by process-name pattern (it can kill another copy's process too). No
  `npm install`/`ci`/`add`/`remove` inside a work copy - dependencies come from the app's own
  linked `node_modules` only. A process you started (a dev server, etc.) is stopped only
  through `wt-run.sh`.
- Never invent a number, threshold or API shape that is not in `facts.md`. If one is missing,
  stop and report "fact-check needed" instead.
- Code that calls an external API/CLI follows exactly the shape recorded in a successful probe
  log. If there is no log, do not guess at the shape - report instead.
- Tests: red, then green. Run the type-checker, the linter on your own files, and the test
  suite once each. If it fails, do not simply re-run it - fix the exact spot, then run once
  more.
- **Actually run the critical path once** (click it in a live preview for a screen, or produce
  a real output file for an engine). If you could not, the report's first line is "not
  verified: <what>" - that is a block, not a completion.

Report (project's working language): commit hash / pass-scenario-by-pass-scenario result with
evidence / checks run and their numbers / not verified / what's left.

## Running tests and long commands
- Run tests, builds and deploys in the **foreground** with a real timeout, and read the
  output. Do not background them if that is disabled in this environment.
- Do not build a polling loop that waits on a process by matching its own command text - the
  loop's own command can match the same pattern and never exit.
- Do not wrap `wt-land.sh`/a deploy script in a short timeout - a cut-off mid-deploy can leave
  the actual result unknown.
